# Мониторинг REST-сервиса

Лабораторная работа №1 по предмету "Принципы построения высоконагруженных систем".

Два экземпляра Spring Boot приложения хранят записи в памяти.
Prometheus собирает их метрики, Java-генератор автоматически создаёт
дашборд Grafana, а JMeter поддерживает фоновую нагрузку.

## Запуск

Нужны Docker и Docker Compose. Из корня проекта скопировать `.env.example` в `.env`:

```bash
docker compose up
```

Логин и пароль Grafana задаются в `.env`. `.env.example` содержит пример настроек.

Генератор дашборда и нагрузчик запускаются после готовности приложений и завершения генератора дашборда.

| Компонент    | Адрес                                    |
|--------------|------------------------------------------|
| Приложение 1 | http://localhost:8081                    |
| Приложение 2 | http://localhost:8082                    |
| Prometheus   | http://localhost:9090                    |
| Grafana      | http://localhost:3000                    |
| Дашборд      | http://localhost:3000/d/items-monitoring |

Остановить стенд:

```bash
docker compose down
```

После изменения кода или плана нагрузки:

```bash
docker compose up -d --build
```

## API

- `POST /items` — создать запись.
- `GET /items/{id}` — получить запись.
- `PUT /items/{id}` — обновить запись.
- `/health` — состояние приложения.
- `/metrics` — метрики Prometheus.
- `/handlers` — список бизнес-ручек для генератора.

Для POST и PUT используется JSON:

```json
{
  "name": "example"
}
```

У каждого экземпляра своё хранилище. Читать и обновлять запись нужно
на том экземпляре, где она создана. После перезапуска данные теряются.

## Метрики и дашборд

Метрики собираются через Actuator и Micrometer:

| Метрика                               | Для чего нужна                               |
|---------------------------------------|----------------------------------------------|
| `http_server_requests_seconds_count`  | Количество запросов, расчёт RPS и ошибок     |
| `http_server_requests_seconds_sum`    | Суммарное время обработки                    |
| `http_server_requests_seconds_bucket` | Распределение времени ответа для перцентилей |

Основные лейблы: `pod`, `datacenter`, `method`, `uri`, `status`.
Лейбл `uri` содержит шаблон `/items/{id}`.
Границы бакетов обозначаются лейблом `le`.

Значения `pod` и `datacenter` передаются через переменные окружения
`POD_ID` и `DATACENTER`. Запросы `/health` и `/metrics` исключены
из метрик завершённых HTTP-запросов.

Для latency выбрана гистограмма: её бакеты можно объединить по
нескольким экземплярам и затем оценить общий p50, p95 и p99 через
`histogram_quantile`.

Для каждой ручки создаются панели RPS, latency и ошибок по кодам.
Можно выбрать несколько подов и датацентров либо `All`.

Генератор получает маршруты из `/handlers`, поэтому добавление ручки
в контроллер с `@BusinessController` не требует изменения генератора.
Дашборд создаётся с отключённым редактированием. Источник Prometheus
настраивается через provisioning с UID `prometheus-main`.

## Нагрузка

План JMeter находится в `load/load.jmx`.
Он запускается после готовности приложений.

За 120 секунд нагрузка постепенно возрастает примерно до 30 RPS
суммарно. Оба экземпляра получают POST, GET и PUT. ID для чтения
и обновления берутся из ответа POST.

Около 3,2% запросов намеренно возвращают ошибки:
`404` для отсутствующего ID и `400` для некорректного JSON.
Нагрузка продолжается до остановки стенда.

Посмотреть состояние и последние результаты:

```bash
docker compose ps -a
docker compose logs --tail 10 load-generator
```

`Exited (0)` у генератора дашборда — нормальное состояние:
он успешно выполнил работу и завершился.
